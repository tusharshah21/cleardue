## Milestone 2 report
### Done
- Mandate engine (`src/agent/mandate.ts`): pure `checkAction(action, ctx)` returning allow / needs_approval / deny with reasons. It covers the tone ceiling, quiet hours in the client's timezone (including windows that wrap midnight), contacting only known recipients, invoice targeting (this invoice only, and only once it's on PayPal), and plan limits (instalment count, exact sum against the outstanding amount, minimum first payment as a percentage or an amount, strictly increasing dates, final date within due date + `maxPlanDays`). It also covers case state (dispute stops everything except escalation, and replies become drafts; a resolved case only allows reads), and autopilot plus confidence gating. Cancel and record-payment always need the freelancer. Verified by 37 tests at 100% statements, branches, functions and lines (`npm run test:mandate`).
- Agent Toolkit wrapped as requested (`src/agent/toolkit.ts`, `src/agent/tools.ts`): the toolkit's `get_invoice`, `send_invoice_reminder`, `cancel_sent_invoice` and `record_payment_for_invoice` tools are lifted into AI SDK v7 tools. Their descriptions and zod-v3 schemas are converted to JSON Schema with validation. Each tool's `execute()` runs the mandate first and only calls the toolkit on `allow`; `needs_approval` queues the call, and `deny` records it with reasons. ClearDue adds a required `tone` field to the reminder tool so the tone ceiling applies to PayPal reminders too (it's stripped before calling PayPal). The toolkit reports failures as `{error}` JSON instead of throwing, so the adapter turns those into real errors. Verified with mocked tool-loop tests (allow executes, needs_approval and deny never execute, denial reasons reach the model).
- ClearDue-native gated tools: `send_message` (Outbox), `pause_reminders`, `offer_payment_plan`, `escalate_dispute`.
- `classifyReply` with a Zod schema, timeout, one retry, then a fallback to `other` at confidence 0 (which forces approval). A deterministic grounding guard drops evidence quotes that don't appear verbatim in the client's own words, and caps confidence at 0.5 when a non-`other` label is left without evidence. Verified by tests (valid output, retry after invalid output, fallback after two failures, readable "AI unavailable" fallback, invented evidence dropped, the freelancer's own words rejected as evidence).
- `proposeAction`: a tool loop (at most 4 steps) driven by a per-reason playbook prompt and a `FACTS` line (ids, precomputed dates, an exact even split, mandate limits). It retries once, but only if no tool has run yet, so it never double-executes. With no tool call or an AI failure, it records a `manual_review` proposal that needs approval. Verified by tests, including no retry after a tool ran and a retry before one did.
- DEMO_MODE (`src/ai/replay.ts`, `src/ai/demo-fixtures.ts`): a LanguageModel that replays recorded responses for the Acme and Brightside stories, filling `{{placeholders}}` from the prompt's FACTS so replayed tool calls carry real invoice ids, dates and amounts. Anything else falls through to the live model. Verified by tests that the recorded classifications pass the schema and that the recorded actions get the expected mandate verdicts against the seed data.
- Flow C UI: on the invoice page, paste a client reply or run "Diagnose now". The case panel shows the reason, confidence, summary, evidence quotes and proposals, each with its mandate verdict and reasons, an editable draft, and approve or reject buttons. Also an approval queue with a pending count in the nav, an Outbox, and a per-invoice timeline of every diagnosis, proposal, decision and status change. Approval re-runs the mandate (approval satisfies needs_approval, never deny) and logs edits. Verified in the browser with DEMO_MODE: Acme was diagnosed `awaiting_approval` (0.93) with two evidence quotes, and Brightside was diagnosed `cash_constraint` (0.95) with a GBP 900 + 900 plan queued because autopilot is off. Approving it put the offer in the Outbox, and the approval count went from 2 to 1.
- Webhooks: `POST /api/webhooks/paypal` verifies via verify-webhook-signature, stores every event in `WebhookEvent` (idempotent by event id, with verified/processed flags and a note), and on invoicing events re-reads the invoice from PayPal instead of trusting the payload. Verified by mocked tests (SUCCESS, FAILURE, missing headers, missing webhook id, API error) and a local unsigned POST, which was rejected and stored as "rejected: PAYPAL_WEBHOOK_ID is not set".
- Polling and case closure: `POST /api/sync` (bearer `CRON_SECRET`, constant-time compare) re-syncs open invoices older than 2 minutes and reopens cases whose pause has ended. It runs from a Render cron job every 5 minutes (`render.yaml`) and after each dashboard load (`after()`). A PAID, CANCELLED or REFUNDED status resolves the case and supersedes pending proposals. Unauthorized calls return 401 (verified locally).

### Deviations from the brief
- AI SDK v7 instead of v4: `@paypal/agent-toolkit` 1.11.0 is built on `ai@4` and zod v3, so I adapted its tools rather than using `getTools()` as-is. Its descriptions, schemas and `execute` are reused unchanged; only the gate sits in front.
- `proposeAction` doesn't return one JSON object. Each gated tool call is the proposal (type = tool name, params = tool input validated against the tool's schema, draft = the message text). That's what makes "the agent genuinely calls PayPal tools" literally true. A run can produce more than one proposal (e.g. AP reminder + pause for `awaiting_approval`).
- Offering a plan executes as a message to the client plus a 7-day pause. The split invoices are created when the client accepts on the pay page (Milestone 3), matching Flow D step 3.
- Simulator webhook events are rejected in production and labelled in dev, because PayPal's docs say simulator events cannot pass verify-webhook-signature ([Webhooks simulator](https://developer.paypal.com/api/rest/webhooks/simulator/)). Verification is never weakened in production.
- An overdue invoice with no client reply skips the AI diagnosis: it's set to `forgot` at 0.7 with a stated reason, and the agent proposes a nudge.
- An approver email that a client writes in their reply becomes a known contact only if it appears verbatim in their message.

### Known issues / risks
- No sandbox or Anthropic credentials yet. Every PayPal and LLM path is verified with mocks and DEMO_MODE only. Plan: as soon as `.env` is filled, run `npm run paypal:spike`, `npm run seed:paypal` and a live diagnosis on each story.
- `remind` with `additional_recipients` delivery to the AP contact is still unconfirmed (your change #4). The spike checks it. Until then the Acme story depends on it; fallback is an Outbox message to the approver with the pay link.
- Mandate settings UI doesn't exist yet: autopilot and limits can only be set through the seed. Plan: a per-client mandate form in Milestone 3, since the demo should show autopilot.
- The Outbox doesn't send email (by design, "Mark as sent" is manual). Resend behind a flag stays optional.
- Server actions that call the AI can take up to around 90 s in the worst case (classify and propose, each with a retry). The UI shows "Diagnosing…". DEMO_MODE is instant.
- `syncStale` syncs every account's invoices (single demo account). It would need scoping before multi-tenant use.
- Render cron jobs are billed separately (small). If that's a problem, an external pinger can call `/api/sync`.
